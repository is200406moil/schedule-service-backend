# Мой семестр

[![CI](https://github.com/is200406moil/schedule-service-backend/actions/workflows/ci.yml/badge.svg)](https://github.com/is200406moil/schedule-service-backend/actions/workflows/ci.yml)

Веб-приложение для студентов РТУ МИРЭА: показывает расписание группы и личные задачи в одном календаре.

Проект начался с курсовой работы в 6-м семестре. Курс по бэкенд-разработке проходил в РТУ МИРЭА на платформе Яндекс Практикума. Для курсовой я выбрал собственную идею: объединить расписание группы и личные дедлайны, чтобы не вести их в разных местах.

## Интерфейс

Основные страницы работают на React и TypeScript:

- `/ui` — расписание выбранного дня, неделя и ближайшие задачи;
- `/ui/calendar` — месяц, пары, перерывы и задачи выбранного дня;
- `/ui/tasks` — задачи с фильтрами, группировкой по срокам и отметкой выполнения;
- `/ui/profile` — сохранённые данные, учебная группа и фотография.

Длительность перерывов считается по времени занятий. Редактирование профиля
и выход доступны через меню аккаунта справа сверху; форма профиля открывается
по `/ui/profile?edit=1`.

Все четыре раздела используют общее окно добавления задачи. Календарь
подставляет выбранную дату и предмет пары. На телефоне окно выезжает снизу,
поля прокручиваются отдельно от кнопок. Закрытие заполненной формы требует
подтверждения. Создать или изменить задачу можно и на отдельной странице.
Старые адреса с `/preview` перенаправляют на основные, сохраняя параметры ссылки.

Вход, регистрация и политика конфиденциальности тоже находятся во фронтенде.
При регистрации нужны почта и пароль; остальные данные необязательны.
Уведомление о технических cookies запоминает закрытие в браузере.

При включённой почте вход требует подтверждения адреса. Ссылка подтверждения
действует 24 часа, восстановления пароля — 30 минут. Обе одноразовые и требуют
действия в форме, а не просто открытия страницы. Смена пароля завершает прежние
сессии. По умолчанию почта выключена: учебная версия разрешает вход без
подтверждения, но восстановление недоступно. Для разработки есть локальные
`.eml`-письма, для доставки — SMTP. Настройка описана в
[локальной разработке](docs/local-development.md#проверка-восстановления-пароля).

## Происхождение проекта и мой вклад

Расписание загружает отдельный сервис [is200406moil/rtu-mirea-schedule](https://github.com/is200406moil/rtu-mirea-schedule). Моя версия основана на форке [0niel/rtu-mirea-schedule](https://github.com/0niel/rtu-mirea-schedule). В основе обоих репозиториев — открытый проект [RTUITLab/Schedule-RTU-API](https://github.com/RTUITLab/Schedule-RTU-API). Исходные проекты распространяются по лицензии MIT.

В сервисе расписания я заменил Excel-парсер на получение данных из публичного `schedule-of` API и разбор iCalendar. Добавил повторные запросы при временных ошибках и буквальный поиск без выполнения пользовательских регулярных выражений. Кэш обновляется в фоне: параллельные запуски блокируются, а новые данные заменяют текущие только после загрузки всех групп.

В этом репозитории находится основное приложение. Оно использует API расписания. Здесь я реализовал:

- бэкенд на FastAPI для регистрации, авторизации и задач;
- хранение пользователей и задач в PostgreSQL, миграции Alembic;
- проверку принадлежности задачи текущему пользователю;
- календарь, объединяющий расписание и личные дедлайны;
- первоначальный интерфейс на Jinja2 и новые страницы на React с адаптивной вёрсткой;
- совместный запуск приложения, двух баз данных и сервиса расписания через Docker Compose;
- API-тесты и автоматическую проверку кода.

## Как всё связано

| Компонент | За что отвечает | Хранилище |
| --- | --- | --- |
| Основное приложение | пользователи, задачи, веб-интерфейс и единая точка доступа к расписанию | PostgreSQL |
| Сервис расписания | группы, пары, преподаватели и аудитории | MongoDB |
| Публичный источник МИРЭА | исходные данные расписания в iCalendar | — |

Браузер обращается только к основному приложению. Оно вызывает сервис
расписания по внутреннему адресу, проверяет ответы и ограничивает время
ожидания. Если расписание недоступно у уже работающего приложения, задачи
остаются доступны. При запуске Compose основное приложение ждёт готовности
PostgreSQL и API расписания.

## Структура

```text
backend/
  app/                    API, бизнес-логика и HTML-оболочки React
  alembic/                миграции базы
  tests/                  серверные тесты
  requirements.txt        зафиксированные зависимости сервера
  requirements-dev.txt    тот же список + инструменты разработки
frontend/
  src/entries/            точки входа страниц
  src/features/           auth, overview, calendar, tasks, profile
  src/shared/             общие компоненты, стили и клиент API
  src/test/               общие помощники клиентских тестов
  package-lock.json       зафиксированные npm-зависимости
  dist/                   результат сборки, не хранится в Git
infra/schedule/           сборка отдельного API расписания и его зависимости
docs/                     архитектура, локальный запуск и подготовка публикации
Dockerfile                сборка основного приложения вместе с интерфейсом
docker-compose.yml        запуск приложения, расписания и баз
```

`infra/schedule/Dockerfile` собирает API расписания из закреплённого коммита другого
репозитория. Его зависимости не смешиваются с основным бэкендом.

## Запуск

Нужен Docker с поддержкой `docker compose`.

Конфигурация ниже предназначена для локальной разработки. В ней открыты порты
приложения, PostgreSQL и API расписания и заданы учебные пароли.
Не используйте её без изменений на публичном сервере.

```bash
docker compose up --build
```

После запуска:

- вход и регистрация: <http://localhost:8000/ui/login>;
- политика конфиденциальности: <http://localhost:8000/ui/privacy>;
- обзор: <http://localhost:8000/ui>;
- календарь: <http://localhost:8000/ui/calendar>;
- задачи: <http://localhost:8000/ui/tasks>;
- отдельная форма новой задачи: <http://localhost:8000/ui/tasks/new>;
- профиль: <http://localhost:8000/ui/profile>;
- API основного приложения: <http://localhost:8000/docs>;
- API расписания: <http://localhost:5000/docs>;
- проверка процесса: <http://localhost:8000/health>;
- проверка готовности приложения и PostgreSQL: <http://localhost:8000/ready>.

Первый запуск может занять несколько минут, пока сервис заполняет кэш
расписания. PostgreSQL, MongoDB и оба API запускаются одной командой.
Данные баз сохраняются в Docker volumes. `schedule-refresh` делает один запрос
на обновление; периодического задания в этой конфигурации нет.

Остановить сервисы:

```bash
docker compose down
```

Для разработки без Docker настройте корневой `.env` по `.env.example`,
установите зависимости, соберите интерфейс и примените миграции.
Версии Python и Node.js, команды подготовки, проверок и локального запуска
описаны в [инструкции по локальной разработке](docs/local-development.md).

## Технологии

Python 3.12, FastAPI, SQLAlchemy, PostgreSQL, Alembic, Jinja2, React, TypeScript,
Vite, Docker Compose, Pytest и Ruff. MongoDB используется только отдельным
сервисом расписания. Все основные страницы используют React; Jinja2 передаёт
им начальные данные и пути к сборке, но не рисует основной интерфейс.

## Проверки

```bash
python -m pip install -r backend/requirements-dev.txt
cd backend
python -m ruff check .
python -m ruff format --check app tests
python -m pytest --cov=app --cov-branch --cov-report=term-missing --cov-fail-under=80
cd ../frontend
npm ci
npm run lint
npm run build
npm test
```

Для локального запуска FastAPI без Docker сначала соберите интерфейс в `frontend`:
результат попадёт в `frontend/dist` и не хранится в Git. FastAPI раздаёт эти
файлы по `/static/react/` без копирования в серверные исходники.
В Docker сборка выполняется автоматически.

Для автопересборки интерфейса при правках есть `npm run dev` из `frontend`.
Страницы по-прежнему открываются через FastAPI; после сборки обновите страницу
в браузере. Это не отдельный сайт на Vite и не режим горячей замены компонентов.

Локально серверные тесты по умолчанию используют отдельную SQLite-базу
в памяти. Проверки, которым нужен PostgreSQL, при этом пропускаются.
В CI набор выполняется на PostgreSQL; общее покрытие с учётом ветвлений
должно быть не ниже 80%. CI также проверяет миграции в обе стороны,
Python-зависимости обоих сервисов на известные уязвимости, синтаксис
сохранённых браузерных JS-файлов и запуск стека в контейнерах.

В `backend/requirements.txt` версии всех зависимостей зафиксированы через `==`.
Docker устанавливает этот список; `requirements-dev.txt` подключает его и
добавляет зафиксированные инструменты для локальных проверок и CI. Отдельных
дублирующих Python lock-файлов больше нет. Для фронтенда используется
`frontend/package-lock.json` и установка через `npm ci`: Python и npm требуют
разных форматов зависимостей. После обновления пакетов нужно проверить
`pip check`, тесты и сборку Docker.

## Что осталось перед публичным запуском

Репозиторий содержит приложение и локальный стек, но ещё не готовую
production-конфигурацию. Для работы с настоящими пользователями нужны HTTPS,
закрытые порты баз, рабочая почта, резервные копии с проверкой восстановления
и регулярное обновление расписания. Ограничители запросов пока работают
в памяти одного процесса, а письма отправляются без долговечной очереди.

Условия обработки данных и политика тоже требуют уточнения под выбранное
размещение. Подробности и ограничения описаны в
[архитектуре](docs/architecture.md#ограничения-и-публичный-запуск) и
[подготовке публичного запуска](docs/privacy-deployment.md).

## Безопасность

- пароли хешируются с помощью Argon2;
- JWT ограничены по времени жизни, в браузере токен хранится в `HttpOnly` cookie с `SameSite=Lax` и настраиваемым флагом `Secure`;
- production-режим не запускается со слабым JWT-секретом или без `Secure` для cookie;
- изменяющие данные HTML-формы и браузерные API-запросы защищены CSRF-токеном;
- повторные неудачные попытки входа временно ограничиваются;
- запросы восстановления ограничиваются по IP и адресу; ответ не раскрывает наличие аккаунта;
- в базе хранится только хеш токена восстановления, а смена пароля отзывает старые JWT;
- ответ при входе не раскрывает, существует ли учётная запись и активна ли она;
- аватары проверяются по формату, содержимому и размеру до 2 МБ;
- страницы приложения используют строгую Content Security Policy и другие защитные HTTP-заголовки;
- все операции с задачами проверяют их принадлежность текущему пользователю;
- служебное обновление расписания защищено отдельным ключом;
- рабочие секреты передаются через переменные окружения, значения из Docker Compose предназначены только для локального запуска;
- процессы основного приложения и сервиса расписания запускаются в контейнерах без прав `root`.
